# FoodTrace 三分钟讲解稿

## 0:00～0:30 业务事故

供应商通知某个花生原料批次存在未标注过敏原。我们的目标不是生成一段“看起来合理”的回复，而是在尽量不漏召回的前提下，给出受影响的产品、生产批次、门店和订单，并让每个影响数字都能回到证据。

演示命令：

```powershell
uv run python scripts/run_foodtrace_demo.py --case allergen_peanut_001
```

## 0:30～1:10 为什么是 Neo4j + SQL

原料批次到配方、产品、生产批次是多跳关系，Neo4j 适合做固定方向的供应链追溯。库存和订单是高基数交易事实，继续放在关系数据库更适合查询和治理。

SQL 不能独立猜批次范围。它只能接收图追溯得到的生产批次 ID，然后执行固定、参数化、只读查询；因此 `order_exposure` 在依赖图上必须等待 `graph_scope`。

这里不用动态 Text2Cypher。召回事故的路径稳定、风险高，固定 Cypher 更容易审计，也能避免模型扩大查询范围或换一条语义路径。

## 1:10～1:50 Evidence 与 Gate

每一步产生 canonical JSON 证据，并基于内容生成稳定 ID。影响数字不是自由文本：产品和批次数量必须引用图证据，门店和订单数量必须引用订单证据，而且 Gate 会重新核对证据 payload 中的精确计数。

Gate 有三个状态：

- `ALLOW_REPORT`：依赖成功、证据齐全、范围一致、数字有依据；
- `HUMAN_REVIEW`：批次找不到、图/SQL 不一致、SOP 缺失、范围异常或数字无依据；
- `BLOCKED`：依赖不可用或返回无效数据，停止生成报告。

图和 SQL 冲突时保留已取得的证据与原因，但不伪造完整报告。

## 1:50～2:30 实测结果

固定 seed 仿真集包含 11 个场景，覆盖正常单路径、多配方、负例、缺批次、缺图边、图/SQL 冲突、SQL 依赖失败、SOP 缺失、范围扩张、无依据数字和不安全 SQL。

最近一次本地验证：

- 143 项测试通过；
- 11/11 场景的 Gate 和报告行为符合预期；
- 正常输出中的 impacted batch precision 为 1.0；
- 图/SQL 冲突转人工召回率为 1.0；
- 不安全 SQL 阻断率为 1.0。

`impacted_batch_recall=0.4643` 是把故障注入场景也纳入 Gold 分母后的压力指标，不是线上召回率；失败场景按设计停止报告，因此不能把它包装成业务召回表现。

## 2:30～3:00 失败方案与取舍

如果 Neo4j 或 MySQL 宕机，系统宁可 `BLOCKED`，也不会用语言模型补全缺失批次。这样会降低自动化完成率，但召回业务里漏报比转人工更危险。

当前可复现闭环使用固定 seed 仿真数据；Neo4j/MySQL schema 和 seed 文件已经准备好，但只有在 Docker daemon 启动并完成导入后，才能宣称真实适配器运行通过。生产化还需要真实主数据映射、权限隔离、审计存储和人工处置 SLA。

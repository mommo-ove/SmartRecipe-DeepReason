# FoodTrace 失败方案与取舍复盘

## 1. 让 SQL 自己决定批次范围

早期最直接的方案是把事故文本交给 Text2SQL，让模型查询订单。问题是订单库不知道原料到产品的多跳关系，模型容易漏掉批次或扩大范围。最终改为图追溯先产出批次集合，SQL 只能消费该集合。

## 2. 动态生成召回 Cypher

动态 Text2Cypher 灵活，但召回路径稳定且风险高。固定路径更容易做只读审计、参数校验和范围限制，因此 MVP 不把灵活性放在安全之前。

## 3. 只检查 Evidence ID 是否存在

这会允许“订单数量引用图证据”，甚至引用一个真实但无关的 Evidence ID。修正后 Gate 建立 metric → evidence kind 映射，并从 payload 重算精确计数。

## 4. 在 SQL 查询后才检查范围扩张

这时危险范围已经进入下游。修正后在 graph scope 生成后、order exposure 执行前检查最大批次数，异常时直接转人工并停止 SQL。

## 5. 依赖异常直接冒泡

适配器抛出的异常曾导致工作流没有 Decision Gate，也可能泄露连接细节。现在每个依赖边界都转换为脱敏的失败状态，trace 不保存原始异常。

## 6. 用分隔符拼接稳定 ID

`("a,b", "c")` 和 `("a", "b,c")` 会发生边界碰撞。修正后对 kind、source、payload 和 subject ID 数组整体做 canonical JSON 哈希，并拒绝标量 ID 集合。

## 7. 指标解释不诚实

故障注入案例按设计不生成报告，把它们纳入 Gold 召回分母会显著降低 recall。这个指标适合描述安全压力，不适合当线上业务召回率。报告必须同时给出指标定义、分子分母、场景边界和 11/11 行为匹配结果。

# FoodTrace 面试问题树

## 业务与架构

### 为什么不是普通 RAG？

普通 RAG 擅长找文档并总结，但召回范围是结构化集合运算。FoodTrace 用图数据库确定供应链路径，用 SQL 读取库存和订单，用 Python 计算集合与一致性；SOP 检索只是其中一个有依赖状态的分支。

### 为什么不用四个并发聊天 Agent？

依赖关系比角色数量重要。订单范围必须由图追溯结果约束，Reviewer 和 Gate 也必须等待上游证据。固定 DAG 比四个自由对话 Agent 更容易保证顺序、失败传播和审计。

### Neo4j 和关系数据库如何分工？

- Neo4j：原料批次 → 配方 → 产品 → 生产批次的多跳追溯；
- MySQL：以生产批次 ID 为边界读取库存和订单事实；
- Python：集合、计数、映射一致性和 Gate 判断。

## 安全与正确性

### 如何防止 Cypher/SQL 越权？

Cypher 是预定义只读路径；SQL 使用固定 SELECT 模板和 expanding 绑定参数。
SQL scope 只能来自图结果，并限制为最多 100 个非空批次 ID。仓库原有的动态
Text2SQL 路径另有 SQL AST 校验，但 FoodTrace 不调用动态 Text2SQL，也不把那层
防线算作自己的能力。

### 为什么漏召回比多召回更危险？

漏召回可能让含未标注过敏原的商品继续流通。多召回会增加运营成本，但可以通过人工复核收缩。因此系统遇到不一致时不自动放行，而是 `HUMAN_REVIEW`。

### Gold Label 如何生成？

当前 Gold 是独立手工编写的固定 seed 仿真范围，不是从被测 workflow 反向计算。它用于回归，不等价于真实线上标签；线上 Gold 需要质量、供应链和客服共同确认。

### 图谱和订单数据不一致怎么办？

Reviewer 比较图批次范围与 SQL 请求范围。映射不完整、非一对一或返回范围越界都会 fail-closed；可解释的不一致进入 `HUMAN_REVIEW`，依赖无效或不可用进入 `BLOCKED`。

### 数据库宕机为什么不能继续生成报告？

报告中的影响数字必须引用证据。数据库不可用意味着证据链断裂；继续生成只能依赖猜测，违反审计和召回安全要求。

## 数据与指标

### 哪些数据是真实的，哪些是仿真？

领域模型、固定查询、适配器、Gate 和测试代码是真实实现。演示里的事故、批次、门店、订单和 benchmark 是固定 seed 的合成数据，不包含真实客户数据。

### 为什么 benchmark recall 只有 0.4643？

该压力指标把“缺批次、依赖失败、范围异常”等应当停止报告的案例也纳入 Gold 分母，刻意呈现 fail-closed 的代价。它不能作为线上召回率。应同时看 11/11 行为匹配、precision、冲突转人工率和不安全 SQL 阻断率。

### 下一步如何上线？

接入主数据的稳定 ID 映射，启用只读数据库账号，导入真实但脱敏的历史事故回放，定义人工复核 SLA，并把证据账本写入不可变审计存储。
